# 발표 구성 · 문장 규칙

## 분량

| 발표 시간 | 슬라이드 | flow 슬라이드 | code 슬라이드 |
|---|---|---|---|
| 5분 | 6~7 | 1 | 0~1 |
| 10분 | 9~12 | 1~2 | 1~2 |
| 20분 | 15~20 | 2~3 | 2~4 |

## 이야기 순서

문제 → 제약 → 구조(전체 그림) → 흐름(어떻게 움직이나) → 결정(왜 이렇게) → 구현 과정 → 결과 → 다음.
"무엇을 만들었다"보다 "왜 이렇게 만들었다"에 시간을 더 쓴다. 각 `focus` 슬라이드는 story.decisions 의 결정 하나와 짝을 이룬다.

## 문장 톤 (모든 테마 공통, `toss` 테마일 때는 특히 엄격히)

- 한 슬라이드 한 메시지. 제목은 주장형으로: "전체 구성" 보다 "무거운 처리는 요청 경로 밖으로"
- 길이 한계(빌드 린트가 검사): 제목 28자, 불릿·카드 본문·설명 45자, 항목 이름 40자. 불릿은 28자 안팎이 가장 읽기 좋다. 넘치면 쪼개거나 `sub` 로 내린다
- 해요체/명사형 중 하나로 통일. 발표자 노트는 해요체
- 수치는 단위와 함께, 비교 대상과 함께: "1시간 → 5분"
- 영어 약어는 첫 등장에 한 번 풀이: "SSE(서버가 브라우저로 밀어 주는 알림)"
- 과장 금지: "혁신적인", "완벽한", "획기적" 같은 수식어 쓰지 않는다
- 강조(`**`)는 슬라이드당 1~2곳

## 타입 선택 · 리듬

| 내용의 성격 | 타입 |
|---|---|
| 도입, 핵심 주제 선언 | `title` |
| 한 문장으로 기억시킬 메시지 | `statement` (덱에 1~2장) |
| 점검·마이그레이션·검증 결과 | `terminal` |
| 정량 변화, 전후 수치 | `stats` (+`bar` 로 상대 크기) |
| 시스템 구조·요청 흐름 | `topology`, `flow` |
| 알고리즘 설명 / 리팩터링 전후 | `code` + `walk` / `magic` |
| 3~4가지 효과·특징 | `bento` |
| 기간별 진행 | `timeline` |
| 비교 | `split` |

- 같은 타입을 3장 연속 쓰지 않는다. 텍스트 장(`bullets`) 사이에는 시각 장(topology/stats/bento/code)을 끼운다
- 전환은 기본값으로 두고, 장이 바뀌는 지점(`section`)이나 `statement` 에서만 `zoom`/`slide-up`
- 모션 때문에 말이 묻히면 줄인다. 한 슬라이드에서 스텝은 2~5, 강조는 1~2곳

## 문서 기반 발표일 때

- 문서의 목차·장 제목이 이야기 순서의 초안이다. 문서가 길면 결론·권고사항부터 뽑고 근거 표를 뒤에 붙인다
- 표는 그대로 옮기지 않는다. `stats`/`timeline`/`terminal` 로 변환하고 모든 수치에 `source`(`"문서명 표 N"`)를 붙인다
- 문서에 없는 수치·날짜·담당자는 만들지 않는다. 필요하면 `[확인 필요: …]`

## 테마 선택

- `aurora` — 기본값. 검은 배경에 흐르는 그라데이션, 가벼운 큰 제목. 개발자·일반 청중 모두에 무난하고 어두운 회의실에 맞다. 여백을 넉넉히 두고 글을 줄일수록 좋아 보인다
- `dark` — 격자 배경의 기술 공유용
- `light` — 프로젝터 밝기가 약하거나 인쇄 배포
- `toss` — 경영진·비개발 직군 대상. 흰 배경, 블루 포인트, 큰 타이포, 카드형 불릿. 문장을 더 짧게 쓴다
