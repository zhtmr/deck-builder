# 발표 구성 · 문장 규칙

이 문서는 4단계에서 `outline.md` 를 쓰기 전에 읽는다. 아웃라인을 쓰는 동안에는 디자인(테마·모션·레이아웃)을 생각하지 않는다.
목표는 **슬라이드 제목만 이어 읽어도 이야기가 통하는 아웃라인**이다.

## 1. 핵심 메시지 한 문장 (아웃라인보다 먼저)

```
[청중]에게 [시스템/변경]이 [문제]를 [방법]으로 해결해 [효과]를 냈다는 것을 보여 주고, [행동]을 요청한다.
```

예: "경영진에게 Recap 이 회의록 작성 시간을 녹음 업로드 한 번으로 없앴다는 것을 보여 주고, 전 부서 확대 적용 승인을 요청한다."

이 문장이 안 써지면 재료가 부족하거나 맥락이 불명확한 것이다. `story.json` 의 `problem`·`metrics` 를 다시 보거나 사용자에게 묻는다. 효과나 행동 자리를 지어내지 않는다 — 출처 없는 효과는 `[확인 필요]`, 행동이 정해지지 않았으면 1단계 질문으로 돌아간다.

## 2. 청중별 프레임

청중에 맞는 프레임 하나를 고른다. 섞지 않는다. 아래 순서가 슬라이드 순서의 뼈대다.

### A. 경영진 · 비개발 직군 — 결정을 받아내는 발표
1. 문제 — 지금 무엇이 불편하거나 비싼가. 숫자 하나로 (`statement` 또는 `stats` 1항목)
2. 왜 지금 — 그대로 두면 어떻게 되나 (`bullets`)
3. 해결 — 사용자가 겪는 변화. 구현 세부는 빼고 (`flow` 또는 `image`, 노드 6개 이하)
4. 효과 — 전후 비교, 절감된 시간·비용 (`stats`, `split`)
5. 요청 — 승인·지원·다음 단계 (`end` + `asks`)

금지: `code` 슬라이드, 클래스·프레임워크 이름이 들어간 제목. 토폴로지 노드 `label` 은 역할명(예: "분석 서버")으로.

### B. 개발자 · 기술 리뷰 — 설계에 합의하는 발표
1. 맥락 — 요구와 제약 (`bullets`)
2. 전체 구조 — `topology` + `flow` 자동 순환 1장
3. 대표 흐름 — 요청 하나가 시스템을 지나가는 경로 (`flow`)
4. 설계 결정 — 결정 하나당 1장. `story.decisions` 의 결정마다 `topology`+`focus` 또는 `split`(대안 vs 선택) 또는 `code`
5. 트레이드오프와 한계 — 무엇을 포기했나 (`bullets`, `terminal`)
6. 남은 과제 · 논의할 것 (`end` + `asks`)

필수: 결정 슬라이드마다 "고려한 대안"과 "고른 이유"가 화면이나 발표자 노트에 있어야 한다. `why` 가 `null` 인 결정은 `[확인 필요: 이유]` 로 남긴다.

### C. 과제 보고 · 진척 공유
1. 목표 — 원래 무엇을 하기로 했나
2. 진척 — 완료 / 진행 중 / 예정 (`terminal` 또는 `timeline`)
3. 결과 — 정량 지표 (`stats`)
4. 이슈 — 막힌 것과 대응 (`bullets`)
5. 다음 계획 — 일정과 담당 (`timeline` → `end` + `asks`)

### D. 고객 · 데모
1. 사용자의 하루에서 겪는 문제
2. 해결된 장면 — 실제 화면 (`image` + `marks`)
3. 핵심 기능 3개 이하 (`bento`)
4. 도입 방법 / 다음 단계 (`end` + `asks`)

### 구현 회고 (청중 무관, 사용자가 "회고"를 원할 때만)
문제 → 제약 → 구조 → 흐름 → 결정 → 구현 과정 → 결과 → 다음.
"무엇을 만들었다"보다 "왜 이렇게 만들었다"에 시간을 더 쓴다.

## 3. 제목은 주장이다

슬라이드에서 청중이 가져갈 결론을 한 문장으로 쓴다. 주제만 말하는 제목은 빌드 린트가 경고한다.

| ❌ 주제형 | ✅ 주장형 |
|---|---|
| 왜 만들었나 | 회의록 작성에 매번 1시간 넘게 들었다 |
| 전체 구성 | 무거운 처리는 요청 경로 밖으로 뺐다 |
| STT 워커 구간 | 워커는 GPU 서버만 늘리면 확장된다 |
| 결과 | 회의록을 손으로 쓰는 일이 사라졌다 |
| 향후 계획 | 인증만 붙이면 외부 기관에 공개할 수 있다 |

- 28자 이내 한 문장. 넘치면 메시지가 둘이라는 신호다 — 슬라이드를 쪼갠다
- 숫자가 있으면 제목에 넣는다
- 서술어로 끝낸다(…했다 / …해요 / …된다). 명사로 끝나면 주제형일 가능성이 높다
- 예외: `title`, `section`(장 구분), `statement`, `quote`, `end` 는 주장형 규칙을 적용하지 않는다

## 4. 헤드라인 테스트 (아웃라인 승인 전 필수)

`outline.md` 의 제목 열만 위에서 아래로 소리 내어 읽는다.

- 앞뒤가 "그래서 / 그런데 / 그 결과" 로 자연스럽게 이어지는가
- 1절의 핵심 메시지가 제목 흐름 안에서 드러나는가
- 빼도 이야기가 통하는 장이 있는가 → 빼거나 부록(`notes` 나 별도 장표)으로
- 같은 말을 두 번 하는 장이 있는가 → 합친다
- 첫 내용 장이 청중의 문제로 시작하는가 ("저희가 만든 것은…" 으로 시작하지 않는다)
- 마지막 장이 요청·다음 행동인가 ("감사합니다" 만 있는 장으로 끝내지 않는다)

하나라도 걸리면 고친 뒤 다시 읽는다. 통과하기 전에는 `deck.json` 을 쓰지 않는다.

## 5. 코드베이스를 이야기로 바꾸기

코드 구조를 그대로 옮기면 "디렉터리 투어"가 된다.

- **모듈 순서가 아니라 데이터·사용자 흐름 순서로** 설명한다. "controller → service → repository" 가 아니라 "녹음을 올리면 → 바로 접수되고 → 워커가 전사해 → 슬랙으로 온다"
- **대표 시나리오 하나를 끝까지 따라간다.** 기능 열 개를 얕게 보여 주지 않는다
- **"왜" 의 출처**: 커밋 메시지, PR 설명, ADR·설계 문서, README, TODO/FIXME 주석, 설정 파일 주석 (`workflow-historian` 이 모은다). 찾지 못한 이유는 지어내지 않는다
- **숫자는 출처가 있어야 한다.** 시스템 모델에서 센 값(노드 수, 흐름 단계 수)은 `system-model.json` 을 출처로 쓸 수 있다. 성능·사용자 수·절감 시간은 테스트·로그·문서에 있을 때만

## 6. 분량

| 발표 시간 | 슬라이드 | flow 슬라이드 | code 슬라이드 (프레임 B 기준) |
|---|---|---|---|
| 5분 | 6~7 | 1 | 0~1 |
| 10분 | 9~12 | 1~2 | 1~2 |
| 20분 | 15~20 | 2~3 | 2~4 |

한 장에 메시지 하나. 넣고 싶지만 흐름에 안 맞는 내용은 발표자 노트로 내리거나 버린다.

## 7. outline.md 형식

```markdown
# Recap — 회의록 자동 기록 서비스
- 청중: 경영진 · 비개발 직군
- 시간: 10분
- 원하는 행동: 전 부서 확대 적용 승인
- 프레임: A
- 핵심 메시지: 경영진에게 Recap 이 … 를 보여 주고, 전 부서 확대 적용 승인을 요청한다.

| # | 제목 (주장 문장) | 타입 | 근거 |
|---|---|---|---|
| 1 | (표지) | title | — |
| 2 | 회의록 작성에 매번 1시간 넘게 들었다 | bullets | story.problem[0] (README.md:3) |
| 3 | 녹음을 올리면 회의록이 슬랙으로 온다 | flow | system-model flows.record-to-minutes |
| … | | | |
| 10 | 다음 달부터 전 부서에 적용해 주세요 | end + asks | — |

## 확인 필요
- [확인 필요: 이유] Kafka 를 고른 이유 (story.decisions[1].why = null)
```

근거 열이 비어 있는 사실 슬라이드는 만들지 않는다.

## 8. 문장 톤 (모든 테마 공통, `toss` 테마일 때는 특히 엄격히)

- 길이 한계(빌드 린트가 검사): 제목 28자, 불릿·카드 본문·설명·요청 45자, 항목 이름 40자. 불릿은 28자 안팎이 가장 읽기 좋다. 넘치면 쪼개거나 `sub` 로 내린다
- 해요체/명사형 중 하나로 통일. 발표자 노트는 해요체
- 수치는 단위와 함께, 비교 대상과 함께: "1시간 → 5분"
- 영어 약어는 첫 등장에 한 번 풀이: "SSE(서버가 브라우저로 밀어 주는 알림)"
- 과장 금지: "혁신적인", "완벽한", "획기적" 같은 수식어 쓰지 않는다
- 강조(`**`)는 슬라이드당 1~2곳

## 9. 타입 선택 · 리듬

| 내용의 성격 | 타입 |
|---|---|
| 도입, 핵심 주제 선언 | `title` |
| 한 문장으로 기억시킬 메시지 | `statement` (덱에 1~2장) |
| 점검·마이그레이션·검증 결과 | `terminal` |
| 정량 변화, 전후 수치 | `stats` (+`bar` 로 상대 크기) |
| 시스템 구조·요청 흐름 | `topology`, `flow` |
| 설계 결정 (대안 vs 선택) | `split` (왼쪽 대안, 오른쪽 선택과 이유) 또는 `topology` + `focus` |
| 알고리즘 설명 / 리팩터링 전후 | `code` + `walk` / `magic` |
| 3~4가지 효과·특징 | `bento` |
| 기간별 진행 | `timeline` |
| 마무리 | `end` + `asks` (요청 1~3개) |

- 같은 타입을 3장 연속 쓰지 않는다. 텍스트 장(`bullets`) 사이에는 시각 장(topology/stats/bento/code)을 끼운다
- 전환은 기본값으로 두고, 장이 바뀌는 지점(`section`)이나 `statement` 에서만 `zoom`/`slide-up`
- 모션 때문에 말이 묻히면 줄인다. 한 슬라이드에서 스텝은 2~5, 강조는 1~2곳

## 10. 문서 기반 발표일 때

- 문서의 목차·장 제목은 재료일 뿐 이야기 순서가 아니다. 프레임(2절)을 먼저 고르고 문서 내용을 그 칸에 배치한다. 문서가 길면 결론·권고사항부터 뽑고 근거 표를 뒤에 붙인다
- 표는 그대로 옮기지 않는다. `stats`/`timeline`/`terminal` 로 변환하고 모든 수치에 `source`(`"문서명 표 N"`)를 붙인다
- 문서에 없는 수치·날짜·담당자는 만들지 않는다. 필요하면 `[확인 필요: …]`

## 11. 테마 선택

- `aurora` — 기본값. 검은 배경에 흐르는 그라데이션, 가벼운 큰 제목. 개발자·일반 청중 모두에 무난하고 어두운 회의실에 맞다. 여백을 넉넉히 두고 글을 줄일수록 좋아 보인다
- `dark` — 격자 배경의 기술 공유용
- `light` — 프로젝터 밝기가 약하거나 인쇄 배포
- `toss` — 경영진·비개발 직군 대상. 흰 배경, 블루 포인트, 큰 타이포, 카드형 불릿. 문장을 더 짧게 쓴다
