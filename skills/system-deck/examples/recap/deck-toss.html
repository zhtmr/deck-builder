1

왜 만들었나

  • 주 1회 2시간 회의, 회의록 작성에 매번 1시간 이상 소요
  • 외부 SaaS는 사내 데이터 반출 이슈 — 직접 구현으로 결정
  • 범위는 의도적으로 좁게
    • 실시간 전사 대신 회의 후 일괄 처리
    • 브라우저 녹음만 지원
문제와 제약을 먼저 공유해 아키텍처 선택의 이유를 깔아둔다.

4

요청 흐름 따라가기

업로드는 브라우저가 스토리지로 직접 보내고, 무거운 STT·요약은 Kafka 뒤의 워커가 비동기로 처리합니다.

  1. 1
    브라우저 녹음기 → Nginx
    녹음 종료 후 업로드 URL 요청
  2. 2
    Nginx → API 서버
    POST /api/uploads/presign — Presigned URL 발급
  3. 3
    브라우저 녹음기 → MinIO
    오디오를 API 서버를 거치지 않고 MinIO에 직접 업로드
  4. 4
    API 서버 → Kafka
    complete 호출 시 stt.requested 이벤트 발행
  5. 5
    Kafka → STT 워커
    STT 워커가 이벤트 수신
  6. 6
    STT 워커 → MinIO
    오디오 파일 다운로드 후 faster-whisper 전사
  7. 7
    STT 워커 → Claude API
    전사문을 Claude로 요약해 회의록 초안 생성
  8. 8
    STT 워커 → Kafka
    결과를 stt.completed로 발행
  9. 9
    Kafka → API 서버
    API 서버가 결과 수신
  10. 10
    API 서버 → PostgreSQL
    회의록 저장
  11. 11
    API 서버 → Nginx
    SSE로 브라우저에 완료 알림
  12. 12
    API 서버 → Slack
    Slack 채널에 회의록 링크 공유
→ 키로 한 단계씩. 3번(직접 업로드)과 4번(비동기 분리)에서 멈춰 설계 이유 설명.
